# Задание: клиенты 1С в rootless podman-контейнере на Arch (KDE Wayland)

## Цель

Запускать клиентские приложения 1С:Предприятие 8.3 на хосте Arch Linux (KDE Plasma, Wayland) из rootless podman-контейнера, ничего не устанавливая в систему хоста.

Нужны все четыре сценария:

- конфигуратор;
- тонкий клиент;
- толстый клиент;
- обычное приложение.

## Границы задачи

Делать только то, что описано ниже. В частности:

- Лицензирование не входит в задачу. Лицензию выдаёт сервер 1С.
- Принтеров, USB, HASP, звука, GPU нет — не пробрасывать. Session-dbus хоста пробрасывается (уведомления, порталы; заказчик снял запрет 2026-10-02, ADR-0008).
- Сеть только исходящая, до сервера 1С. Входящих соединений нет.
- Запуск программ хоста из контейнера не нужен. Shared memory с процессами хоста не нужна.
- Ярлыки в меню KDE не нужны. Запуск ручной, версий платформы несколько.
- Отдельный systemd unit или Quadlet не делать.
- distrobox, Flatpak, VM, Wine не использовать.
- Масштаб в KDE 100%, HiDPI не рассматривать.

## Окружение

- Хост: Arch Linux, KDE Plasma на Wayland. Приложения 1С работают через XWayland.
- Основной рантайм контейнеров: podman (rootless).
- База образа: Ubuntu (если это станет блокером, то Debian или Fedora). Предпочтительно Ubuntu 26.04. Если это не получится, то конкретную версию выбрать по официальной документации платформы (раздел про установку на Linux) для нужного релиза. Отдельно проверить наличие библиотек, нужных встроенному браузеру/HTML-полю.
- Ориентир по версии платформы: 8.3.27.2342 (как у серверного контейнера). Подтвердить у заказчика перед сборкой.
- Дистрибутив платформы ищи в `distr/`.
- Уже есть сервер 1С в контейнере, и там работает технологический журнал с готовым logconf. Образ и подход можно переиспользовать, если они подходят. Подключение ТЖ рассматривать как отдельный этап, если этот ТЖ не понадобится в ходе установки.

## Важно про факты о дистрибутиве

Пути, имена бинарников, имена пакетов и состав бандленных библиотек внутри дистрибутива 1С зависят от версии. **Ничего не предполагать и не подставлять по памяти.** Все такие сведения получать только из реально установленной платформы (`ls`, `ldd`, `LD_DEBUG=libs` и т.п.) и фиксировать в отчёте.

## Архитектура

### Что контейнер берёт от хоста

- **Дисплей:** файловый сокет X11 (XWayland) и xauth-файл сессии. Если клиент не подключается к X-серверу без сети хоста, выяснить причину. Запасной вариант — `--network=host`, но использовать его только при доказанной необходимости и отметить в отчёте.
- **Сеть:** дефолтная исходящая.
- **Тома:**
  1. каталог обмена файлами (кусок home хоста, на время отладки это может быть подкаталогом `volumes/`, как и остальные);
  2. каталог с logconf (`logcfg.xml`), монтируется как есть;
  3. каталог для файлов технологического журнала на хосте, должен переживать процесс и контейнер;
  4. отдельный каталог под клиентский профиль в контейнере (списки баз и настройки клиента), чтобы не пропадали после завершения контейнера. 
  5. каталог контейнера `/var/1C/licenses` - если используется community лицензия, то её надо хранить.
- **Пользователь:** `--userns=keep-id`, чтобы файлы в смонтированных каталогах (в том числе ТЖ) принадлежали пользователю хоста.
- Прочие ограничения: без `--privileged`, без общих IPC/PID с хостом.

`volumes/` для условно постоянных файлов хранить в git, но каталоги "каталог обмена файлами", "каталог для файлов технологического журнала" добавлять в gitignore.
Проект внутренний, не публикуется, поэтому хранение секретов (типа лицензии) в git не проблема/

### Жизненный цикл контейнера

Контейнер живёт, пока в нём есть клиенты 1С. Конфигуратор может запускать другие клиенты, и после закрытия конфигуратора эти клиенты не должны умирать.

Реализуется двумя скриптами.

#### Скрипт точки входа (в контейнере)

Один и тот же скрипт используется и как команда `podman run`, и как команда `podman exec`. Различаются ветки только проверкой «я PID 1».

```
Запустить 1С с переданными параметрами (в фоне).
Если я не PID 1:
    выйти.
Цикл:
    подождать немного (порядка полсекунды)
    если в /proc нет клиентов:
        выйти (контейнер погаснет)
```

Требования и подводные камни:

- Клиент в обеих ветках стартует в фоне (`&`), после чего скрипт либо выходит (не PID 1), либо идёт в цикл (PID 1).
- Проверка «я PID 1» работает только без `--init`. Не использовать `--init` вместе с этой схемой.
- Как PID 1 скрипт обязан обработать SIGTERM (`trap`) и завершиться сразу, чтобы `podman stop` не ждал таймаут. Если ожидание в цикле блокирующее, оно не должно откладывать реакцию на сигнал.
- При подсчёте клиентов исключать: сам PID 1, собственные вспомогательные процессы скрипта (в том числе ожидание в цикле), кратковременный экземпляр скрипта из `exec`, процессы в состоянии Z (зомби, третье поле в `/proc/<pid>/stat`).
- Не привязывать критерий «клиенты есть» к именам бинарников 1С. Контейнер предназначен только для 1С, любой посторонний процесс считается клиентом.
- Опционально: вместо опроса раз в полсекунды можно сделать уведомление о завершении процессов. Для первой версии не требуется.

#### Скрипт запуска (на хосте)

```
Если контейнер этой версии уже запущен:
    podman exec -d <контейнер> <скрипт точки входа> <параметры 1С>
Иначе:
    podman run --rm -d --name <контейнер> <флаги> <образ> <скрипт точки входа> <параметры 1С>
При ошибке команды: warning в консоль.
Ничего не ждать: запустили и забыли.
```

- Параметры: версия платформы (определяет образ и имя контейнера), тип клиента и ключи запуска. Ключи передаются в 1С без изменений.
- `--rm` обязателен, иначе остановленный контейнер займёт имя.
- `flock` не нужен. Известные гонки решаются перезапуском клиента вручную:
  - `exec` попал в момент гашения контейнера;
  - два `run` одновременно, второй падает на занятом имени.
- В этих случаях скрипт должен вывести понятный warning вроде «контейнер не запущен, перезапустите». Учесть, что `podman exec -d` возвращает успех, если сам `exec` стартовал, а не если клиент 1С отработал.
- Если контейнер не запущен после `run`, вывести warning.

## Этапы

1. **Разведка.** В одноразовом контейнере на выбранной базе установить платформу 1C. Запустить (любой из клиентов), собрать диагностику. Результат: список необходимых пакетов и, возможно, список конфликтующих бандленных `.so`. На этом этапе открыть БД не получится - нет лицензии в контейнере, это нормально.
2. **Containerfile.** Зафиксировать результат разведки декларативно: установка через apt, удаление конфликтующих библиотек, локаль ru_RU.UTF-8, шрифты (то, что реально необходимо по итогам разведки). Версия платформы задаётся аргументом сборки, тег образа содержит версию. Список удаляемого хранится по каждой версии отдельно.
3. **Скрипты.** Точка входа и хостовый скрипт по описанию выше.
4. **Приёмка** по списку ниже, отчёт.

## Критерии приёмки

- Запускаются конфигуратор, тонкий клиент, толстый клиент и обычное приложение, подключаются к серверу 1С и открывают базу.
- Сохраняется community лицензия.
- Работают элементы, зависящие от встроенного браузера (HTML-поле и подобное).
- Русская раскладка и буфер обмена работают в обе стороны между контейнером и KDE.
- Диалоги открытия и сохранения видят каталог обмена, файлы там создаются от пользователя хоста.
- После завершения процесса файлы ТЖ остаются в смонтированном каталоге, принадлежат пользователю хоста.
- Сценарий «запустил конфигуратор → из него запустил клиентов → закрыл конфигуратор»: клиенты продолжают работать, контейнер гаснет после закрытия последнего.
- Второй запуск через хостовый скрипт при живом контейнере поднимает ещё одно окно в том же контейнере.
- Сборка образа другой версии платформы выполняется сменой одного аргумента.
- `podman stop` останавливает контейнер быстро, без ожидания таймаута.

Большая часть проверок выполняется пользователем! Не агентом! 

## Результат

- Containerfile и инструкция по сборке.
- Скрипт точки входа и хостовый скрипт запуска.
- Краткий отчёт:
  - выбранная база и почему;
  - найденные проблемы зависимостей и что с ними сделано;
  - список удалённых бандленных библиотек;
  - что проверено из критериев приёмки, что нет;
  - нестандартные решения (например, `--network=host`, если понадобилось).

## Ограничения на процесс

- Не расширять задачу: лицензии, печать, USB, автозапуск, ярлыки, HiDPI не трогать.
- Если что-то в задании противоречит действительности (например, нужный пакет отсутствует в базе), остановиться и описать проблему, а не придумывать обход.
- Ничего не устанавливать на хост.
- При возникновении проблемы, которая не решается за 1-2 итерации - выносить на обсуждение
