# ADR-0008: session-dbus хоста в контейнер (уведомления; порталы — нет)

**Статус:** принят (изменение ограничения задачи: dbus разрешён).

## Контекст

Исходное ограничение задачи — «dbus не пробрасывать». Оно блокировало
нативные KDE-диалоги файлов (xdg-desktop-portal) и уведомления из 1С.
Заказчик снял ограничение: «пусть dbus будет; заодно оповещайки можно
делать».

## Решение

`bin/1c-run.sh` монтирует session-bus сокет хоста:

```
-v /run/user/<uid>/bus:/run/user/1000/bus
-e DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/1000/bus
```

Совпадение uid (keep-id) делает адрес одинаковым с хостовым. Entrypoint
выставляет `GTK_USE_PORTAL=1` — GTK-приложения попросят диалоги через
`org.freedesktop.portal.FileChooser`.

## Результат (проверено)

- Уведомления из контейнера доходят до хоста (KDE-тосты): проверено
  программной отправкой `org.freedesktop.Notifications.Notify` из
  контейнера.
- Портал хоста виден из контейнера (`org.freedesktop.portal.Desktop`
  в ListNames, FileChooser v4).

## Ограничение (факт)

Файловые диалоги 1С остаются GTK-видом: платформа (wxWidgets-диалоги)
не использует `GtkFileChooserNative`, поэтому `GTK_USE_PORTAL=1` на неё
не действует. KDE-диалог в 1С без правок платформы не получить. Если
понадобится — варианты: xdotool/заплатка в 1С, либо свой файловый
диалог через внешний механизм запуска. Пока оставлено как есть.

## Безопасность / изоляция

- Контейнер получает доступ к session-шине хоста: может отправлять
  уведомления, звать порталы, видеть имена шины. Это осознанно
  принято заказчиком.
- Системная шина (`/run/dbus/system_bus_socket`) не пробрасывается.
- На хосте ничего не устанавливается: portal-kde уже часть Plasma.
