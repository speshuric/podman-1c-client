# Как окно контейнера попадает на экран хоста

Как podman/docker доставляет окна GUI-приложений из контейнера на
рабочий стол пользователя. Пояснение к строкам `bin/1c-run.sh`:

```bash
-v "$X11_SOCKET:/tmp/.X11-unix"
-e "DISPLAY=$DISPLAY_VALUE"
```

## Ключевая идея

Контейнер не имеет своего графического стека: окно рисует не он, а
X-сервер хоста. Контейнеру достаточно (а) найти сервер и (б) иметь
право с ним соединиться. Оба условия закрываются двумя строками выше.

## Откуда контейнер знает, где сервер

X11-клиент ищет сервер по переменной `DISPLAY`. Для локальных
соединений значением может быть только имя сокета: `DISPLAY=:0`
означает «соединись с файловым сокетом `/tmp/.X11-unix/X0`». Это не
сеть: клиент и сервер общаются через unix-сокет в файловой системе.

## Как сокет становится общим

Bind-mount каталога `-v /tmp/.X11-unix:/tmp/.X11-unix` показывает
контейнеру каталог с сокетами X-серверов хоста. Теперь
`/tmp/.X11-unix/X0` внутри контейнера — тот же самый сокет, к которому
подключаются нативные приложения хоста. Отдельного сетевого проброса
не нужно; сетевые порты (TCP 6000+) в этой схеме не участвуют вообще.

Механика одинаково работает в podman и docker: bind-mount и
переменная окружения описаны одинаково (docker: те же флаги
`--volume`, `--env`).

## Как контейнер получает право рисовать

X11-сервер требует аутентификации: у клиента должен быть cookie из
xauth-файла сервера. Отсюда вторая пара строк:

```bash
[ -r "$XAUTH_VALUE" ] && mounts+=(-v "$XAUTH_VALUE:/tmp/.xauth:ro" -e "XAUTHORITY=/tmp/.xauth")
```

- `$XAUTHORITY` на хосте указывает на xauth-файл текущей X-сессии
  (в KDE Plasma на Wayland путь вида `/run/user/<uid>/xauth_<случай>`,
  имя меняется между входами, поэтому скрипт берёт его из окружения);
- файл монтируется read-only в `/tmp/.xauth`, и `XAUTHORITY` в
  контейнере указывает на него — теперь клиент 1С может предъявить
  cookie и соединиться.

Без монтирования xauth окно не появится: клиент умирает с
«Authorization required».

## Кто рисует окно в Plasma (Wayland)

На хосте с Wayland-композитором (KDE Plasma) X11-клиентов обслуживает
**XWayland** — X-сервер, работающий внутри Wayland-сессии: он слушает
тот самый `/tmp/.X11-unix/X0`. Приложение в контейнере считает, что
рисует в X11; XWayland принимает его содержимое и передаёт композитору
(KWin), который уже показывает окно в Wayland-сессии — в панели задач
и на столе как обычное окно. Ни контейнер, ни приложение о Wayland не
знают (`WAYLAND_DISPLAY` в контейнер не передаётся).

Цепочка: клиент 1С → unix-сокет `/tmp/.X11-unix/X0` → XWayland (хост) →
KWin → экран.

## Что ещё появляется на хосте

- **Буфер обмена и раскладка** — обрабатывает XWayland/Plasma:
  переключение раскладки хоста действует на окна контейнера, буфер
  обмена синхронизируется между X11-клиентами и Wayland.
- **Уведомления** — через session-bus хоста: монтируется
  `/run/user/<uid>/bus` (строки про `DBUS_SESSION_BUS_ADDRESS` в
  `bin/1c-run.sh`); вызов `org.freedesktop.Notifications.Notify` из
  контейнера рисует тост Plasma.
- **Файловые диалоги** — рисует само приложение (wxWidgets в 1С),
  портал KDE не подключается (ADR-0008).

## Что не пробрасывается и почему

GPU, звук, принтеры, USB, HASP — по ограничениям проекта (TASK.md);
системная шина D-Bus не монтируется. Общая память и PID-пространство
хоста не нужны.

## Docker

Схема не привязана к podman: `--volume`, `--env DISPLAY`,
`--env XAUTHORITY` переносятся один в один. На docker rootless
потребуется то же отображение uid (`--userns=keep-id` поддерживается),
иначе файлы в томах получат чужого владельца. На docker это не
проверялось — проект на podman.
